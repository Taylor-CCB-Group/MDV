# Backend API for column curation (rename + soft delete), decoupled from the `editable` flag

**Status:** accepted — implemented. `rename_column`, `soft_delete_column` and their routes are in
place with unit tests; the frontend uses a shared `isCuratableDataColumn` predicate and splits the
header menu into curation and data gates. The Playwright specs have not been run against it.

## Context

Two operations on column metadata are needed:

- **Rename** — change a column's `name` (display label). The `field` (identifier) is never
  touched, so nothing that references the column breaks.
- **Soft delete** — set the tombstone (`deleted: true`). The column stays in the datasource and in
  exported files; MDV stops showing it.

Both existed only in the React table's header menu — a human clicking through, project by project.
Views are increasingly generated by script, and the curation step could not be, so column labels
differ between projects holding the same underlying quantities, and columns that should not be
user-visible stay visible.

Rename's backend primitive already existed as `set_column_metadata`, unexposed as a named
operation. Soft delete's did not: `deleted` appeared nowhere in Python, and only the frontend
honoured it. `remove_column` is a *hard* delete that removes the data — a different operation
whose name must not be reused.

See `docs/rename-and-hide-columns.md` for how to call the resulting API.

## Decision

Two `MDVProject` methods, each exposed as one thin `project_bp` route with
`access_level='editable'`:

1. `rename_column(datasource, field, new_name)` — wraps `set_column_metadata`. Validates that the
   column exists, has an explicit `field`, is not a tombstone, is not an `sgindex`/`sgtype`
   spatial column, that the name is non-empty, and that no other live column uses it
   (case-insensitively). Mirrors the frontend's rules.
2. `soft_delete_column(datasource, field)` — sets `deleted: true`, refuses spatial columns, and
   raises if any saved view references the field.

The method is the API; the route is transport. Scripts may call either.

### Not gated on the `editable` flag

`editable` means *"users may edit values in this column"* — a data-plane permission. Both curation
operations required it in the UI, fusing two unrelated concerns: whether users may overwrite a
column's *values*, and whether an editor may relabel or hide the *column*.

It also made curation impossible in practice. No Python ingest path writes the key, and the two
sides disagree on what its absence means: the writer defaults to `true`
(`ChartManager.js:1160`), the React table reads `false` (`useSlickGridReact.ts:266`). So every
ingested column was permanently non-renameable.

Curation is therefore gated by **project permission only**. `isRenameableDataColumn` became
`isCuratableDataColumn` — structural checks alone (`sgindex`, `sgtype`, `deleted`) — shared by
rename and delete, and the header menu split into curation gates and data gates. Bulk Edit and the
replace half of Find & Replace still require `editable`, which is what it is for.

Sharing one predicate matters for delete specifically: spatial columns were previously protected
from deletion *only* by being non-editable, so ungating without it would have put "Delete Column"
on geometry columns.

### Targeted single-key writes, not the `save_state` whole-array replace

`save_state` replaces the entire columns array with the frontend's reconstruction. The new
operations mutate one key on one column and carry none of that risk — the main reason the
endpoints are worth having when a script could already POST `/save_state`.

### The tombstone stays presentation-only

Python readers continue to see tombstoned columns. This is already documented user-facing
behaviour — the delete dialog says the column "will still appear in exported datasource files".
Making Python readers honour the flag would touch the chat pipeline; out of scope.

### Soft delete blocks on view references, via a generic deep scan

The frontend blocks deletion while a column is referenced; the Python method matches that contract
and raises, listing the offending `(view, chart)` pairs.

Detection is a generic recursive scan of each chart config, not a port of the frontend's
chart-type-aware `configEntriesUsingColumns`. That table would drift as chart types are added, and
**drift fails open** — a missed config entry tombstones a column a chart depends on. The generic
scan **fails closed**: it may over-report and block a deletion that would have been fine. For a
destructive operation that is the right direction. No `force` escape hatch.

Scope is deliberately narrow: chart configs under `initialCharts[datasource]` only — not
`columnGroups`, `links` or `images.*.key_column` — matching the frontend.

## Considered and rejected

- **Python methods only, no routes.** Scripts run against a remote deployment; routes cost little
  over the methods.
- **Reusing `POST /save_state` from scripts.** Requires reconstructing and resending the whole
  columns array — maximum blast radius for a single-key change.
- **A new `hidden: true` flag.** A second invisible suppression mechanism that can disagree with
  the tombstone, leaving a missing column with two possible causes.
- **Renaming the `field` identifier.** Referenced by chart params, column groups, links and image
  key columns; renaming it breaks all of them.
- **Ungating rename but leaving delete gated on `editable`.** Leaves the stated rule untrue in the
  UI and keeps the two curation operations behind different gates for no principled reason.
- **Setting `editable: true` across a project so renaming becomes possible.** Buys consistent
  labels by making the underlying data user-writable — a data-integrity cost for a labelling
  problem.

## Consequences

- Curation becomes scriptable, applied identically across projects as part of view generation.
- **Order is forced for hiding: hide first, then generate views.** `add_datasource` defaults to
  `add_to_view="default"`, which generates a table plot listing every column and would block every
  deletion, so scripts that hide columns pass `add_to_view=None`.
  `create_view_with_all_datasources` was changed to skip tombstoned columns. Renaming carries no
  such constraint — it never consults views, because `field` is unchanged — so labels can be fixed
  on a project whose views already exist.
- **A UI rename now persists immediately** via `saveView()`, as delete already did. It previously
  only marked `dirtyMetadata`, so navigating away discarded it. Accepted costs: renaming also
  commits the rest of the view state, and each rename is a full view save.
- "Rename Column" and "Delete Column" now appear on ingested columns, where neither could before.
  Delete is the consequential one — any project editor can tombstone any ingested column — but it
  stays bounded by the view-reference block and is reversible.
- Legacy columns carrying `name` but no `field` are refused: for those, identity *is* the label.
- **Known limitation:** a UI rename does not propagate to other charts' labels until reload, and a
  chart whose title was already persisted keeps the old one. A fix needs a `column_renamed`
  broadcast plus a decision on whether a rename may overwrite a customised chart title. Deferred;
  scripted curation is unaffected, since a script renames before the project is opened.
- Not addressed, both pre-existing: the `editable` `?? true` / `?? false` default mismatch, and the
  absence of any supported way to set `editable` on an ingested column.
